## 交什么

一个 TypeScript 文件，导出 `onTick`，可选导出 `onStart`：

```ts
export function onStart(game: Game): void {
  // 可选，开局调用一次
}

export function onTick(view: View, cmd: Commands): void {
  // 每隔 game.decisionInterval 个 tick 调用一次
}
```

- 只能是单个文件，不能 `import`。所有类型（`View`、`Entity`、`Commands`……）和全局函数（`dist`、`console.log`）都可以直接用，不用导入。
- 只能用"擦掉类型就是 JavaScript"的写法：不能用 `enum`、`namespace`、构造函数参数属性（`constructor(private x: number)`）。
- 顶层变量整局都在，可以用来记状态（比如看到过的敌人位置、每个单位的分工）。
- 不要依赖异步：顶层代码里的 `await` 和 `Promise` 回调会在加载时跑完，但 `onTick` 里排的 `Promise` 回调永远不会执行；没有 `setTimeout`。
- 递归深度大约 1000 层。超过会抛出 `InternalError: stack overflow`，可以 try/catch 接住；地图上的搜索（洪水填充、深度优先）请用显式的栈或队列，不要用递归。

## 时间与调用

- 游戏按 tick 推进。初始局面是第 0 tick，每隔 `game.decisionInterval` 个 tick 调用一次 `onTick`。
- 你在第 t tick 的局面下发出的命令，在推进到第 t+1 tick 时最先执行。
- 所有玩家看到同一时刻的局面、同时下命令、同时结算，没有先手后手。
- 命令会一直执行，直到完成、失效或被新命令替换。所以不需要每次都给每个单位下命令，只在需要改变时下。给单位下和它当前命令完全相同的命令不会有任何影响（不会打断采集进度，也不会重新规划路线）。
- `view` 是调用开始时的快照，同一次调用里下的命令不会改变它（比如 `produce` 之后 `view.resources` 不会变少，要自己记账）。

## 每个 tick 的结算顺序

1. 执行各玩家的命令，同一个玩家的命令按发出顺序执行。不合法的命令被拒绝，下次调用时在 `view.events` 里看到 `rejected` 和原因。
2. 生产：每个建筑队列里第一个的剩余时间减 1，减到 0 就放到建筑旁边能走到的最近空格（从紧贴建筑的格子开始按步数往外找，最多 4 步，不会隔着墙出生）；同样近的选离地图中心最近的，再一样随机挑。都满了就等。
3. 战斗：所有冷却好了、射程内有目标的实体同时出手、同时扣血，然后移除生命 ≤ 0 的实体。
4. 移动：冷却好了的单位按随机顺序各走一格。被单位挡住先等；挡路的是自己的 idle 单位，或者是迎面想走进你这格的自己人，就直接交换位置；被挡 2 tick 起会试着绕路。敌人不会让路。`move`、`attackMove` 被挡 30 tick 就放弃，变成 idle。
5. 建造：命令是 `build`、贴着地基的单位每人给地基干 1 份活，干满就建好（发 `built` 事件，去建它的单位都变成 idle）。
6. 采集：贴着资源点的采集者采集，带着资源贴着交货点的交货。
7. 规则包结算（计分、判胜负）。

## 命令

同一次调用里的命令按顺序执行，对同一个单位后面合法的命令覆盖前面的；被拒的命令不影响已经生效的。`u`、`b`、`target`、`resource` 可以传实体，也可以传 id。

| 命令 | 效果 | 什么时候被拒 |
|---|---|---|
| `cmd.move(u, x, y)` | 走到 (x, y)，途中不还手，到了变成 idle。目标格在建筑、岩石里，就走到离它最近的能站的格后变成 idle；目标被完全隔开、从这里走不过去，直接变成 idle。 | 不是你的；不能移动；坐标不是整数或在地图外 |
| `cmd.attack(u, target)` | 追着打 target，直到它死掉、你方所有实体都看不见它、或者从这里走不到它（之后变成 idle，并照常自动攻击）。不能移动的实体（比如塔）在目标走出射程后也变成 idle。可以打敌方建筑，也可以打中立的可攻击实体。 | 不是你的；不能攻击；看不到目标；目标是自己的、资源点或无敌的；自己不能移动且目标在射程外 |
| `cmd.attackMove(u, x, y)` | 走向 (x, y)；射程内有敌人（单位或建筑）就停下来打，自己视野内有敌人就追过去打（视野里的敌人走不过去就不管它，继续去终点）；终点的处理和 `move` 一样；到了变成 idle。 | 不是你的；不能移动或不能攻击；坐标不对 |
| `cmd.gather(u, resource)` | 循环采集：走到资源点旁边采，采满后自动回最近的交货点交货，再回来。资源点采完后交完手上的就变成 idle。贴着资源点的格子能站几个就能几个人同时采（没有别的名额）；站满了，后来的在附近等空位，不会自己换矿。交货点被拆了就去最近的另一个；一个都没有就变成 idle，手上的资源留着。 | 不是你的；不能采集；目标不是资源点或已经采完 |
| `cmd.stop(u)` | 停下（idle）。 | 不是你的 |
| `cmd.produce(b, type)` | 排进生产队列，立即扣资源。 | 不是你的；建筑还没建好；不能生产这种类型；队列已满（5 个）；单位数（现有 + 所有队列里的）已到 `game.unitCap`；资源不够（同一次调用里的 produce 按顺序扣钱） |
| `cmd.cancel(b)` | 取消队列里最后一个，全额退款。对没建好的建筑：拆掉它，退还造价的 75%（向下取整）。 | 不是你的；队列是空的 |
| `cmd.build(u, type, x, y)` | 在左上角 (x, y) 放下 type 的地基、立即扣钱，u 走过去建（见下面「建造」）。对自己没建好的同类地基（左上角正好是 (x, y)）下，就是去接着建或者帮忙，不扣钱。 | 不是你的；u 不能建造这种类型（`game.types[u.type].builds`）；按这个顺序查：占地超出地图；地形不可走或压着资源点（这两样整局都看得见）；有格子不在你方视野里；有别的实体（单位也算，包括 u 自己）；资源不够（和 produce 一起按顺序扣钱） |

另外，参数类型不对、一次调用超过 2000 条命令都会被拒。实体不是你的和已经死了，拒绝原因是同一句话（"你没有 #id 这个实体"）。

自动攻击：`idle` 和 `attackMove` 状态、能攻击的实体（单位，以及规则包里能攻击的建筑）会打射程内的敌人（敌方单位和建筑都算），选最近的，一样近选血最少的，再一样选 id 最小的。`move`、`gather`、`build` 状态的单位不还手。中立实体不会被自动攻击。

## 建造（规则包里有能建造的单位时）

- 单位能建什么看 `game.types[类型].builds`，建筑的造价是 `cost`，建造工作量是 `buildTicks`。
- `cmd.build` 一被接受，地基就放下了：立即扣钱、占住格子（挡路），你会收到 `created` 事件。工人走到贴着地基的地方，每 tick 干 1 份活，几个工人一起建就按人数加快（再给别的工人下同一条 `build` 就是去帮忙）。
- 地基的生命从最大生命的 1/10 开始，随进度涨到满；建造期间挨的打不会补回来。建好时收到 `built` 事件。
- 没建好的建筑（实体上有 `construction: { done, total }`，谁看见都有）：会挡路、能被打，但不能生产、不能当交货点、不能攻击。被打掉了，去建它的单位变成 idle；你收到的 `died` 事件带 `unfinished: true`。（`died` 事件带 `removed: true` 的是规则包按玩法移除的，不是被打死的。）关键事件里标"（规则包）"的是规则包自己写的事件（比如"扛起了旗"）。
- 放地基前可以用全局函数 `canBuild(view, type, x, y)` 检查位置，和引擎的判断一致；`buildProblem(view, type, x, y)` 做同样的检查，返回放不下的原因（放得下返回 null），比如哪一格不在视野里、被哪个实体挡着。规则包还可能有自己的放置限制（见玩法说明），这两个函数不知道。
- 找位置可以用 `findBuildSpot(view, type, near, maxRange?, margin?)`：在 `near` 附近按距离从近到远找（默认 8 格以内），占地四周 `margin` 格（默认 1）以内不挨着建筑和资源点，免得堵路；返回左上角 `{ x, y }`（`buildProblem` 一定是 null），找不到返回 null（附近不在视野里，或者都被占了）。要在很多地方找时注意燃料。
- 有战争迷雾时，占地的每一格都要在你方（或盟友）某个实体的视野里，所以去远处建要先派人过去，到了再下 `build`。写法：先 `cmd.move` 让工人走到目标附近，之后每次决策都用 `buildProblem` 看一眼，返回 null 就 `cmd.build`；工人已经停下（idle）还放不下，就把原因打进日志、换个位置。别用"离目标几格以内才 build"这种写死的距离判断：工人可能永远停在差一格的地方，build 一次都没发出去，被拒命令的统计里也看不到。算工人到一块还没放下的地基的距离，用 `dist(工人, { x, y, w, h })`（按占地算）。
- 注意别把工人去资源点和交货点的路堵死：建筑四周最好留出一格。

## 中立实体

- `owner` 是 -1 的非资源实体（比如规则包放的野怪、守卫）。能攻击的中立实体闲着时会自动打射程内的玩家实体（谁都打，不分队伍），中立实体之间不会互相打；你的单位不会自动打中立实体，要用 `cmd.attack` 去打。
- 中立实体平时不动，规则包可以指挥它们走、追着打人，具体看玩法说明。击杀中立实体有没有奖励也看玩法说明。

## 坐标、距离、视野

- 格子坐标，左上角是 (0, 0)，x 向右、y 向下。单位只能上下左右走，不能斜着走。
- 距离一律是曼哈顿距离 |dx| + |dy|。多格建筑按占地里最近的那一格算，贴着为 1。全局函数 `dist(a, b)` 就是这个距离。
- 射程、视野、"贴着"都按这个距离。近战射程 1 就是上下左右贴着（斜对角距离是 2，打不到）。所以一个 1×1 的资源点最多同时有 4 个采集者（上下左右各一个，前提是那几格能站）。
- 一格只能站一个单位。建筑、资源点和不可通行的地形挡路。
- 地形和资源点整局都看得见（`game.terrain`；资源点的位置和剩余量 `amount` 一直在 `view.entities` 里）。如果规则包开了战争迷雾，其他实体只看得到己方任一实体视野范围内的。
- 地图可能每局不同：平台自带的规则包都按种子随机生成墙、水和一部分资源点（对称，每家看到的一样），规则包说明书的「开局地图」一节写了哪些固定、哪些会变。开局从 `game.terrain` 和 `view.entities` 读当局的地图，别把坐标写死；`rts-arena map <规则包> --seed N` 看别的种子的地图，`rts-arena check` 每个位置用不同的种子试打。
- 资源点的 `hp`、`maxHp` 都是 0，剩余量看 `amount`。
- 实体 id 是随机分配的正整数，不重复使用，大小不代表先后。
- `damaged` 事件里的 `by` 是攻击者的 id，攻击者不一定在你视野里。两次调用之间的 `damaged` 事件最多保留约 200 条，再多的丢弃（其他事件不丢）。

## 队伍（规则包支持分队时）

- `view.players[i].team`（或 `game.teams[i]`）相同的玩家是盟友；不分队时每人一队，队伍编号就是玩家编号。队伍编号从 0 开始：命令行、战报、对战页里的「队1」就是 team 0。
- 视野共享：盟友的实体你总是看得见，盟友看得见的敌人你也看得见。
- 不能攻击盟友：对盟友下 `attack` 会被拒绝（"不能攻击盟友的 #id"），自动攻击也不会打盟友。
- 各管各的：资源、交货点、生产、单位上限都是自己的；不能在盟友的建筑交货，也不能指挥盟友的单位。
- 盟友的单位会挡路，而且不会和你换位置（只有你自己的单位会让路）。
- 胜负按队伍判，具体见规则说明。判断敌人请用队伍而不是"不是我的"：`e.owner >= 0 && view.players[e.owner].team !== view.players[view.me].team`。

## 随机与复现

- 地图和开局由规则包决定（现有规则包的地图每局都一样）。对局种子影响：单位移动的先后、等价路线和出生格的随机挑选、你的 `Math.random()`。
- 同样的 bot、同样的种子，重跑结果完全一样。

## 沙箱限制

- **燃料**：每次 `onTick` 最多用 `game.fuel` 燃料，1 燃料大约是 5000 次简单循环（约 0.4 毫秒）。燃料按这个粒度计，很轻的调用会显示用了 0。用完立即中断，这次的命令全部作废，下次调用时 `view.events` 里有 `botError`。顶层代码加上 `onStart` 共有 20 倍燃料。
- **内存** 128 MB，超了 bot 停止运行（你的单位只会继续执行已有命令）。
- **墙钟**：单次 `onTick` 超过 2 秒（加载阶段 10 秒），或者整局所有调用累计超过 120 秒，bot 停止运行。正常代码碰不到，只有对巨大数组排序、拼超长字符串、打印大对象这类不计燃料的内置操作才会。墙钟和机器快慢有关，所以只当兜底。
- 没有 `Date`（调用会抛错，时间用 `view.tick`）、没有网络、文件、定时器。
- `console.log` 写进回放：每次调用最多 20 行、每行 300 字，整局 5000 行。打印大对象会先完整转成 JSON 再截断，很慢而且不计燃料，别打印整个 `view`。
- 抛出的错误带行号，就是你源文件里的行号。错误会写进回放，下次调用时也会出现在 `view.events`。
- `canBuild` 要遍历 `view.entities`，在很多位置上反复调用会花不少燃料；先用自己的规则筛掉明显不行的位置再调用。

## 本地调试

在你的 bot 目录里（`rts-arena init <规则包>` 建的，有 `arena.json`）：

```bash
rts-arena check                    # 类型检查 + 在每个位置上和不动的对手试打 300 tick（--ticks N 打更长）
rts-arena run                      # 和基准 bot 打一局
rts-arena run --games 10           # 打 10 局看胜率（每个种子换边各打一次；加 --quiet 每局只打一行）
rts-arena run 对手.ts              # 和别的 bot 打（文件路径或现成 bot 的名字）
rts-arena league                   # 联赛：和所有参考 bot 循环对打，出排行榜和统计（两人局默认每对 4 局；--size K 每局 K 人，--teams 2v2 分队，--per-table N 每桌几局）
rts-arena run 规则包 v3.ts expand   # 自己指定所有参赛的 bot（在 bot 目录里不写规则包时，自己的 bot 会自动排在第一个）
rts-arena report                   # 文字战报：看最新一局（按你的 bot 那局坐的座位写）
rts-arena view                     # 网页播放器看回放，「对战」页也能开比赛
rts-arena help run                 # 只看某个命令的用法和选项
```

- 规则包可以是平台自带的（`arena.json` 里写名字），也可以是别人写的规则包目录（写相对 bot 目录的路径）。不管哪种，参考 bot（现成的陪练对手）都放在规则包目录的 `bots/` 里、和规则包一起发布，名字和打法列在上面的「参考 bot」里，`rts-arena list <规则包>` 也能看。对手位置写名字或文件路径都行。
- `baseline` 是每个规则包的基准 bot：经济、防守、集火都做全了的均衡对手，先打赢它。但它不一定是最强的，其他参考 bot 各走一个方向（速攻、发展、守家……），有的正好克制它。只对着 baseline 调出来的 bot 容易过拟合，每改一版都用 `rts-arena league`（不写对手就和所有参考 bot 循环对打）看总的得分率。`idle` 是什么都不做的对手。
- `check` 只能抓开局阶段的问题，中后期才会出现的错误（比如资源点采完之后）要看 `run` 的输出。
- `run` 每局会打印胜负、燃料，以及报错和被拒命令按种类汇总的次数和第一次出现的 tick。每局还给每个 bot 写一份只有它自己信息的日志 `<回放>.P<座位>-<bot 名>.log`（你的日志、报错、被拒命令、统计和胜负），找自己的那份看就行，不会和对手的混在一起。
- **战报**：每份 bot 日志的开头附了一份从你的座位写的战报，也可以对任何回放运行 `rts-arena report [回放]`（不写回放看最新一局）。内容：每隔一段时间双方的资源、这一段的收入、分数、各类单位（括号里是闲着的个数）和建筑（括号里是没建好的个数），关键事件（第一次交火、建筑放下 / 建好 / 被毁、第一次挨打、金矿采完、实体换主人、中立实体被谁打死；太多时省略中间的，`--full` 全部列出），死 3 个以上的战斗（时间、地点、双方损失），采集、花费、击杀的估算，以及"可能的问题"（报错、被拒最多的命令、工人闲着、闲得最久的工人在哪和闲下来之前在做什么、钱囤着没花、同一个位置的建筑反复被拆、工人被卷进战斗（还有那些工人死的时候在执行什么命令）、挨打时还没有兵、第一场大战开打时兵比对手少、经济比赢家差得多、输之前的兵力对比）。战报是赛后复盘，双方的信息都有，对局中你的 bot 看不到这些。`--every T` 改抽样间隔。规则包按玩法移除的实体（交了货的、过期的）单列一节，不算死亡和损失；规则包给了自己的统计时也会列出来。日志里附的战报标题比 `report` 输出的低一级（`###`），因为日志自己的各节是 `##`。
- **联赛的误差**：每对 4 局时，同一份代码的两份副本得分率能差十几个百分点（局数少时更多）。判断改动有没有用，把旧版本、新版本都放进联赛，再把同一个 bot 写两次（名字会带 #编号）：两份之间的差就是这时的误差。"把握度"在分出胜负的局数少于 6 时会标"偏乐观"。统计里还会列出打到时间上限才结束的对局是哪几组。
- **联赛的输出**：每局一行，最后是那一局的回放文件名；在 bot 目录里跑的联赛最后还会列出你的 bot 没拿到第一的局和回放文件名，精彩对局也优先挑有你的 bot 的局。`check` 会打印你的 bot 在试打里的前几行日志（onStart 里打的也在），看看 bot 是不是按你想的在跑。
- **精彩对局**：联赛最后会挑出几局最值得看的（大约每 4 局挑 1 局，最多 5 局），每局写上看点：逆转（兵力或比分落后过、最后赢了）、优势换手、大战、险胜（赢家主基地差点被拆，或者比分咬得很紧）、爆冷（联赛得分率低的赢了高的）。bot 出错的局会扣分。想看自己的 bot 是怎么被翻盘、怎么翻盘的，先看这几局的回放和战报。
- **座位**：`--games` 会换边，同一个 bot 每局坐的位置不一样。在 bot 目录里运行 `report` 时，不写 `--player` 就按你的 bot 那一局坐的座位写；写了别的座位会提醒。日志文件名里的 `P<座位>` 就是那一局你坐的位置。多局时最后还会按座位报胜场，看地图是不是偏向某一边。
- 多人局（规则包允许 3 人以上时）：`--games` 会在同一个种子上把座位轮换一遍，最后报平均名次。
- 分队：`rts-arena run 队友.ts 对手1.ts 对手2.ts --teams 2v2`，按 你、参数 的顺序分组（你和队友一队）；`--games` 会轮换两队的位置。
- 想用程序读结果：`rts-arena run ... --json` 每行一个 JSON 事件，`type` 是 start（参赛者）、game（每局：赢家座位 winners、名次 ranking、回放和日志文件名）、summary（胜场、平均名次）、warning、error。
- 回放默认写在 bot 目录的 `replays/`（`--out` 可以改），每局一个 JSON 文件；每次 run 另有一份 `*.series.json` 汇总。网页播放器能拖进度条、点实体看它当前的命令、对着画面看你的日志和每条被拒命令。
- 回放 JSON 的结构：`map` 是地图（`width`、`height`、`terrain` 每行一个字符串、`colors`），`types` 是各实体类型的占地、生命、视野、造价等，`players` 是参赛者（名字、bot 文件、队伍），`result` 是结果，`bots` 是每个 bot 的统计；`initial` 是开局快照，`frames[i]` 是第 i+1 tick 的变化（`t` 字段就是这个 tick），字段有 `spawn`（新实体）、`move`（`[id, x, y, id, x, y, …]`）、`hp`（`[id, 生命, …]`，资源点是剩余量）、`die`（死亡 id）、`removed`（`die` 里规则包移除的，不是被打死的）、`shots`（`[攻击者, 目标, …]`）、`ord`（`[id, 命令文字]`）、`bp`（`[id, 建造进度百分比, …]`，100 是建好了）、`owner`（`[id, 新主人, …]`，规则包改了归属的实体，-1 是中立）、`players`（资源和分数）、`logs`（你的日志）、`errs`（报错和被拒命令）。
