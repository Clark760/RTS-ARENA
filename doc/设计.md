# RTS Arena 设计说明

大模型（或人）按平台暴露的接口写 TypeScript 脚本控制一方，在格子地图上进行即时战略对战。平台提供规则引擎、沙箱、命令行工具和网页回放播放器。

## 1. 范围（用户拍板）

| 编号 | 决定 | 来源 |
|---|---|---|
| D-001 | 脚本语言用 TypeScript；引擎、规则包、bot 都用 TypeScript | 用户拍板 |
| D-002 | 展示用 H5（PixiJS）网页回放，不用 Godot | 用户拍板（"单纯的 H5 做展示更方便"） |
| D-003 | 通用性先做到"换目标"：规则包可以换地图、单位数值、胜负条件、计分、事件；动作集固定在内核 | 用户拍板 |
| D-004 | 规则包是可信代码，暂时不进沙箱 | 用户拍板；2026-10-06 用户要求加上规则包沙箱，见 D-122 |
| D-005 | 地图用格子 | 用户拍板 |
| D-006 | 对局规模不设硬限制，由规则包作者决定；平台给出明确的建议上限（见第 7 节），超出只提醒 | 用户拍板 |
| D-007 | 不做网页写 bot；人想测试就用和大模型相同的接口和命令行 | 用户拍板 |

以下是实现时我做的选择，都可以改：

| 编号 | 选择 | 理由 |
|---|---|---|
| D-101 | 只能上下左右走，距离一律曼哈顿距离（射程、视野、"贴着"都按它） | 一种距离贯穿全局，大模型最不容易算错 |
| D-102 | 同时决策、同时结算，命令持续生效到完成或被替换 | 没有先后手；bot 写策略而不是每 tick 操作每个单位 |
| D-103 | 一格只站一个单位；建筑、资源点、不可走地形挡路 | 规则简单、结果确定 |
| D-104 | `idle`、`attackMove` 自动打射程内的敌人（最近 → 血少 → id 小），`move`、`gather` 不还手 | 常见即时战略约定，bot 不用写自动反击 |
| D-105 | 建筑只有开局摆好的，没有建造命令 | "换目标"层级先不需要；以后作为内核动作再加 |
| D-106 | 非法命令不报错崩溃，而是在下次调用时以 `rejected` 事件交还原因 | 大模型能从事件里自己纠错 |
| D-107 | bot 抛错或燃料耗尽：这一次的命令全部作废，bot 继续运行；内存超限、墙钟超时、加载失败：bot 停止运行，单位只执行已有命令 | 一次失误不至于直接输，严重问题不拖垮对局 |
| D-108 | 回放记录"每 tick 的变化"，不在前端重算规则 | 前端不需要和引擎保持一致的确定性 |
| D-109 | 多局模式下两人局每个种子换边各打一次 | 抵消地图和随机数，比较两个 bot 更准 |
| D-110 | 资源点和地形一样不受迷雾影响，位置和剩余量始终可见 | 外部大模型试写时，第一版 bot 因为"看不见中间的矿"被拒了 117 次命令；资源点不会动，藏起来没有策略价值 |
| D-111 | 给单位下和当前命令完全相同的命令时什么都不做 | bot 常常每次都重发命令，这样不会打断采集进度或重新规划路线 |
| D-113 | 每局给每个 bot 单独写一份日志文件，只有它自己的日志、报错、被拒命令和胜负 | 用户提出：几个 agent 同时看回放会分不清哪条是自己的；对战时也不该看到对手的调试输出 |
| D-114 | 混战里主基地被拆就出局，剩下的单位和建筑一起清掉；名次按出局先后 | 避免没人指挥的残兵继续占地图、干扰别人 |
| D-115 | 队伍模式：盟友共享视野、按队伍判胜负（获胜队伍的人都算赢，包括中途出局的） | 用户拍板 |
| D-116 | 盟友之间：不能互相攻击；资源、交货点、生产、单位上限各管各的；不能指挥盟友单位；盟友单位挡路且不换位 | 用户只定了视野和胜负，其余是我按"最少改动"选的 |
| D-117 | 平台装成本地命令 rts-arena，每人只维护自己的 bot 目录（arena.json 记规则包和 bot 文件）；对战服务以后再做 | 用户拍板（先做第一层） |
| D-119 | 建造命令：下命令时立即放地基、立即扣钱；占地要都在己方视野里、没有任何实体（含单位）；工人贴着地基每 tick 干 1 份，多人叠加；拆地基退 75% | 用户要求"工人能造兵营"；具体规则是我定的，理由见第 13 节 |
| D-120 | 新规则包「拓荒」frontier：开局没有兵营，工人可建兵营、箭塔、仓库，摧毁主基地获胜 | 用户要求"做一个支持建造的模式"；玩法和数值是我定的 |

## 3. 内核约定

### 3.1 每个 tick 的顺序

1. （逢决策 tick）按 tick 开始时的局面调用所有 bot，收集命令。
2. tick + 1；按玩家编号顺序执行命令（命令只影响自己的单位，顺序不影响结果）。
3. 生产：建筑队列第一个剩余时间减 1，到 0 就放到建筑旁边能走到的最近空格（按步数，最多 4 步，不隔墙），同样近的选离地图中心最近的，再一样随机挑。
4. 战斗：所有冷却好、射程内有目标的实体同时出手，先算完再扣血，再移除生命 ≤ 0 的。
5. 移动：随机顺序，每个单位走一格；第一轮被挡住的等别人走完再试一次。
6. 采集与交货。
7. 规则包 `onTick`，然后 `result`；到 `maxTicks` 调 `timeUp`。
8. 记回放。

### 3.2 寻路

- 去不会动的目标（格子、建筑、资源点）用**流场**：从目标做一次 BFS，所有去同一目标的单位共用；缓存总共 32 MB（64～1024 张，地图越小张数越多），建筑或资源点增减时整体作废。目标格在障碍里时，先灌满那片障碍再往外扩，单位会停在离目标最近的可站位置。
- 追会动的单位：10 格以内用**小范围 A***（最多扩展 400 格），目标走出 2 格再重新规划；更远，或者 A* 找不到更近的路（隔着长墙要先绕远），改用去目标当前格的流场。流场也到不了才算到不了。
- `attackMove` 被视野里走不过去的敌人引开时，不管它，继续去终点。
- 被挡住：挡路的是自己闲着的单位，或者是上次也想走进我这格的自己人（迎面堵住），直接交换位置；被挡 2 tick 起用"以流场为启发值、把单位当障碍"的 A* 绕一段（最多扩展 300 格）；`move`、`attackMove` 被挡 30 tick 放弃。敌人不让路。
- 多个方向一样好时随机挑（用对局随机数，可复现），包括换位的方向。固定顺序会让两边走出不对称的路线，曾经实测导致换边后胜负跟着边走。

### 3.3 确定性

- 内核只用整数运算，随机数是 mulberry32，种子用 FNV-1a 按用途（规则包、内核、各个 bot）分开混出来。
- 沙箱里 `Math.random` 换成按种子的确定性随机数，`Date` 调用即抛错，删掉 `WeakRef`、`FinalizationRegistry`（依赖垃圾回收时机）。
- 燃料按 QuickJS 中断回调次数计，是确定的；墙钟超时不确定，所以只用来兜底极端情况，触发即判 bot 停止。
- 测试 `对局可复现` 检查同种子两次回放相同（耗时统计字段 `perf`、`bots[].ms` 除外，它们只做参考）。

### 3.4 公平性

同一个 bot 镜像对打，按边统计（引擎审阅员实测）：

| 规则包 | bot | 局数 | P0 : P1 : 平 |
|---|---|---|---|
| annihilation | rush | 300 | 144 : 156 : 0 |
| koth | hold（bot 自己按绝对坐标分配控制点格，本身不对称） | 300 | 131 : 169 : 0 |
| koth | hold 改成镜像对称的版本 | 300 | 139 : 161 : 0（p ≈ 0.2） |
| harvest | greedy | 100 | 45 : 53 : 2 |

没有发现显著的引擎边偏。早先速攻 90 局 57:33（p ≈ 0.01）是在修掉固定方向顺序之前测的，样本也偏小。夺点两次都略偏 P1，值得继续观察。3 人以上的局面还没测（现在没有 3 人以上的规则包）。

## 4. 沙箱

- 每个 bot 一个独立的 QuickJS WebAssembly 实例和内存（`WebAssembly.Memory` 设上限，默认 128 MB）。QuickJS 自带的 `setMemoryLimit` 在 quickjs-emscripten 0.32 里实测不生效（内存炸弹能把进程吃到 2 GB），所以改用 wasm 内存上限；一个 bot 内存超限或崩溃不影响别的 bot。
- bot 代码用 Node 的 `stripTypeScriptTypes` 只擦掉类型（行列号不变，报错行号就是源文件行号），按 ES 模块加载，取 `onTick`、`onStart` 导出。
- 宿主和沙箱之间每次调用只传一个 JSON 字符串进去、一个 JSON 字符串出来。宿主在加载 bot 前就拿到了 prelude 里的函数，bot 替换 `__arena` 没用。
- bot 能改 Array、String、Object 的原型，从而绕过 prelude 里的日志和命令上限，所以宿主收到结果后再强制一遍：返回内容超过 200 万字直接作废；只收前 20 行日志、每行截到 300 字；命令只收前 2000 条。命令参数在沙箱里就先转成数字或字符串。
- 栈：QuickJS 栈上限 256 KB（约 1000 层递归），深递归在沙箱里抛出能接住的错误。设到 512 KB 时会先撑爆宿主（V8）的原生栈，整个 bot 被判崩溃。
- `import` 由 QuickJS 的模块加载器拒绝（文本匹配会误伤注释和字符串，已弃用）。
- 墙钟：不计燃料的内置操作执行期间不会触发中断回调，所以单次超时（2 秒，加载 10 秒）和整局累计超时（120 秒）都只能在调用结束后判，判了就停掉这个 bot。所以一个恶意 bot 最多让一局多卡一次（实测构造出过 35 秒），之后就出局。
- 燃料：1 燃料约 5000 次简单循环、约 0.24～0.44 毫秒（看机器）。

## 5. 规则包

一个规则包是 `rulesets/<id>/` 下的三个文件：

| 文件 | 内容 |
|---|---|
| `index.ts` | 默认导出 `Ruleset`：参数、地形、实体类型、`setup`、`onTick`、`objectives`、`result`、`timeUp` |
| `objectives.ts` | 导出 `Objectives` 类型，描述 `view.objectives` 的结构；会原样进 bot 的 arena.d.ts |
| `RULES.md` | 给 bot 作者看的玩法说明，会进 PROMPT.md |

`arena docs <id>` 根据这三个文件和内核接口生成 `arena.d.ts`（实体类型名、资源名换成字面量类型）和 `PROMPT.md`（玩法、参数、单位表、平台通用说明、完整接口）。把 PROMPT.md 发给大模型就够了。

规则包能用的接口见 `src/core/types.ts` 的 `SetupContext` 和 `RuleContext`：读全部实体和本 tick 事件（死亡带击杀者和"没建好"标记、生产、交货、建好），加分、加资源、刷实体、移除实体、让玩家出局、设置回放叠加层（区域、文字）和状态文字。

歼灭、夺点、采集竞速共用一套单位和开局（`rulesets/common/standard.ts`），只在地图和目标上不同，正好验证"换目标"（混战见第 11 节，拓荒见第 13 节）：

| 规则包 | 目标 | 怎么实现的 |
|---|---|---|
| annihilation 歼灭 | 摧毁对方主基地；到时间比击杀价值 | `result` 查主基地；`onTick` 读死亡事件加分 |
| koth 夺点 | 独占中央控制点每 tick 得 1 分，先到 600；或摧毁主基地 | `onTick` 用 `entitiesIn` 数区域里的单位；叠加层显示控制点归属 |
| harvest 采集竞速 | 先累计交货 1500 金；建筑无敌 | 把建筑 `maxHp` 设为 0；`onTick` 读交货事件加分 |
| frontier 拓荒 | 自己建兵营、箭塔、仓库；摧毁主基地 | 工人类型加 `builds`、开局不放兵营；`onTick` 读死亡事件，按建好没建好算价值 |
| beacons 烽火台 | 清掉台址里不动的中立野怪、守卫，建烽火台独占台址计分，先到 400；或摧毁主基地 | 中立实体只放不指挥；`onTick` 每 10 tick 按台址里建好的烽火台结算；击杀中立怪给赏金；区域叠加层标出台址归属 |

| tech 科技 | 拓荒加 4 种科技建筑，建好的在加成就在；摧毁主基地 | 和拓荒共用 `common/frontier.ts`；`onTick` 数每人建好的科技建筑，变了就用 `setTypeStats` 重设各兵种数值（有这个科技是加成值，没有是原值），`note` 写"建好了 / 加成取消" |

## 6. 回放格式

`Replay`（`src/core/types.ts`）：规则包信息、种子、玩家、地图和地形颜色、实体类型的画法、开局快照，然后每 tick 一帧。帧里只有变化：新实体、移动 `[id,x,y,…]`、生命 `[id,hp,…]`、死亡、攻击 `[攻击者,目标,…]`、命令变化、建造进度 `[id,百分比,…]`（100 是建好了）、换主人 `owner: [id,新主人,…]`（规则包 setOwner，D-130）、玩家资源和分数、叠加层、状态文字、bot 日志和报错。播放器每 100 tick 存一个关键帧，拖进度条时从最近的关键帧往后推。

**按某一方的视野看**（D-121）：回放的 `types` 里有各类型的视野半径 `sight`，顶层有 `fog`。播放器选了视角后，按和引擎同一份代码（`src/core/vision.ts` 的 `markSight`、`rectSeen`）从当前局面算出这一队看得见的格子：没有迷雾、自己和盟友的、资源点都显示，其余实体要有一格在视野里才显示；视野外的格子盖一层暗色（每格一个像素的画布放大），攻击线有一端看不见就不画，侧栏里对手的资源和单位数显示成"？"。视角选单人时日志也切到这个人。不另存每 tick 的视野：bot 第 t tick 看到的就是回放第 t 帧之后的局面算出来的视野，`test/vision.test.ts` 逐 tick 比对了播放器算出的可见实体和 bot 当时的 `view.entities`（两人局和 2v2 都完全一致）。老回放没有 `sight`、`fog`，视角下拉框禁用。

每个规则包有一个 `rulesets/<规则包>/bots/baseline.ts`（原来在 `bots/<规则包>/`，D-131 搬进规则包目录），作为衡量新 bot 的标准对手，命令行里写 `baseline` 就能用。都只用公开接口，单文件，不用随机数。

（战绩是 2026-10-06 改弓手数值之后的，两批种子各 20 局合计，注明的除外。）

调的过程中学到的几条（以后写规则包、调平衡可以参考）：

- 只有一个兵营，造兵速度是瓶颈，所以单位强弱要按"每 tick 造兵时间换来多少战斗力"算，而不是按造价。旧弓手按这个算远不如战士，所以纯战士最强（见第 10 节）。
- 混编在夺点里开局吃亏：前期速攻是一波纯战士，弓手太脆；开局先出 6 个战士再混编最好。
- 夺点是比时间的：打输一仗后"打不过就回家"会缩到输，必须有"对方快赢了就压上"的规则。
- 采集竞速里花钱不扣分，杀对方工人只是让对方少采几趟、再花 50 金补人，所以骚扰本身伤害不大；真正致命的是工人被杀光、没钱重建。护卫站位前移拦截，对 raider 从 0:20 变成 19:1。

**参考 bot（D-131）**：用户指出，有的大模型通过 agent 自己翻到了仓库里的其他示例 bot 拿来陪练，结果超过了没翻到的；而且只有一个基准 bot，大模型容易只对着它调、过拟合。所以：

- 参考 bot 和规则包放在一起（`rulesets/<id>/bots/`，外部规则包本来就是 `<目录>/bots/`），一起发布；`catalog.ts` 的 `referenceBots` 统一找（规则包的 bots/，再加平台通用的 idle），baseline 排第一。
- 每个 bot 文件第一行 `//` 注释是一句打法说明。PROMPT.md 多一节「参考 bot（陪练对手）」：名字和打法的表、"别只对着 baseline 调，每版都用 league 和全部参考 bot 打"、源码在哪。所有写 bot 的人拿到的信息一样。`rts-arena list <规则包>` 列出打法；对战页的下拉框悬停显示打法；bot 目录里 `run` 不写对手时打完提醒还有哪些参考 bot。
- 写规则包这边：RULESET.md 要求至少 3 种打法、第一行写说明，并说明参考 bot 也是检验玩法的工具；new-rules 模板带 baseline、rush（速攻）、greedy（只采不打）；`check <规则包>` 在参考 bot 少于 3 个或没写说明时提醒。
- 测试（`test/bots.test.ts`）：每个自带规则包至少 3 个参考 bot（不算 idle）、都写了打法、都出现在 PROMPT.md 里；每个参考 bot 打不动的对手都能赢、0 报错 0 被拒。

## 10. 单位数值

用户要求让弓手有用武之地（2026-10-06）。用歼灭的基准 bot 派生出四种编队互打（`npm run balance -- '{"名字": {弓手数值}}' 20`，脚本在 `src/cli/balance.ts`；每组 20 局、每个种子换边各一局）：

| 弓手数值（血 / 造价 / 造兵 tick / 伤害 / 冷却，射程都是 4） | 2战1弓 对 纯战士 | 1战1弓 对 纯战士 | 纯弓手 对 纯战士 | 2战1弓 对 纯弓手 | 1战1弓 对 2战1弓 |
|---|---|---|---|---|---|
| 旧：60 / 90 / 70 / 8 / 10 | 1:19 | 0:20 | 0:20 | 20:0 | 5:15 |
| **现在：60 / 80 / 60 / 10 / 8** | 17:3 | 15:5 | 3:17 | 18:2 | 12:8 |
| 60 / 85 / 65 / 10 / 9 | 7:13 | 7:13 | 1:19 | 20:0 | 13:7 |
| 60 / 80 / 60 / 9 / 8 | 13:7 | 10:10 | 0:20 | 19:1 | 12:8 |
| 50 / 80 / 55 / 12 / 8 | 16:4 | 12:8 | 8:12 | 14:6 | 4:16 |

选了第二行：弓手和战士每 tick 输出相同（1.25）、造兵时间相同，血少一半、贵 5 金，换来 4 格射程。结果是要有战士在前面挡（纯弓手打不过纯战士），战士配弓手的混编明显强于纯战士，两种混编比例都可行。数值很敏感：造兵时间多 5 tick 或者伤害少 1，弓手的价值就掉一大截。

## 11. 多方混战

内核从一开始就是按 N 个玩家写的（视野、命令、事件、bot 调用都按玩家分），多方混战只需要规则包和命令行配合：

- **规则包**声明 `players: { min, max }`。`rulesets/melee`（混战）是 2～4 人：64×64 正方形地图，四重旋转对称（`rotationalTerrain`、`rotateK`，在 `rulesets/common/standard.ts`）；两人坐对角，三人空一个角，四人坐满。
- **出局和名次**：结果里的 `ranking` 是按名次分组的玩家编号（同一组并列）。混战里主基地被拆就出局并清场，越晚出局名次越好；到时间时还在场的按击杀价值排在出局者前面。两人规则包不用填，内核按 winner 推。
- **命令行**：`npm run arena -- run melee a.ts b.ts c.ts d.ts --games 8`。同一个种子把座位轮换一遍（4 人就是 4 局），抵消角落和随机数的影响，最后报每个参赛者的胜场和平均名次。每个 bot 的日志各写一份。
- **播放器**：最多 6 种玩家颜色；多人局结束时横幅显示名次。

混战基准 bot（`rulesets/melee/bots/baseline.ts`）和歼灭的基准相同，只是每次挑离自己最近、还没出局的对手打。和三个歼灭 bot 四人混战 8 局（种子 10、11，座位轮换）：基准赢 5 局、平均名次 1.88；先发展的 boom 赢 3 局、平均 2.00；rush、llm 没赢过。歼灭的 bot 都打"第一个还在场的对手"，前期会一起围攻 P0，这正是要靠座位轮换摊平的东西。

**队伍**（D-115、D-116）：

- 内核：每个玩家有队伍编号（`World.teams`，不分队时就是玩家编号）。视野格按队伍共用一张；`visibleTo` 对盟友的实体总是为真；敌人 = 属于别的队伍的玩家，自动攻击、攻击命令都只对敌人（中立实体仍然可以手动打）。结果里的 `winners` 是所有获胜玩家。
- 规则包声明 `teams: true` 才接受分队，`SetupContext` / `RuleContext` 有 `teams` 和 `isAlly`。混战里队友坐相邻的角，按全队出局先后排名次。
- bot 接口：`view.players[i].team`、`game.teams`；混战的目标信息多了 `allyBases`。
- 命令行：`--teams 2v2` 按给出的 bot 顺序分组；`--games` 在同一个种子上轮换各队的位置，按队报胜场。每个 bot 的日志里写明盟友和对手。
- 混战基准 bot 认得盟友，和队友挑同一个敌人（以全队主基地中心为准选最近的），盟友家门口被打时去帮忙。2v2 里基准两人一队对 llm + boom（这两个不认识盟友）6 局赢 5；llm 对盟友下攻击被拒了 51 次，拒绝原因写得很清楚。

## 12. 本地命令

- 安装：克隆仓库后 `npm install && npm install -g .`（全局命令是指向克隆目录的链接）；或者 `npm pack` 出 tgz 给别人 `npm install -g xxx.tgz`。`npm install -g git+https://…` 不能用：npm 在临时克隆里准备 git 依赖时继承了全局模式，依赖没装进克隆目录，`prepare` 构建找不到 tsc（2026-10-06 实测）。Node 不给 node_modules 里的 .ts 擦类型，所以装好的命令跑编译后的 `dist/`；在平台仓库里（或 `npm install -g .` 软链到仓库）时，入口 `bin/rts-arena.js` 直接跑 `src/` 的 .ts。
- 平台自己的文件都通过 `src/paths.ts` 找：文本资源（接口定义、PLATFORM.md、RULES.md、示例 bot）从包根目录读，规则包代码从 `dist/` 或源码目录加载。
- bot 目录：`arena.json`（`ruleset`、`bot`）、bot.ts、PROMPT.md、arena.d.ts、tsconfig.json、.gitignore。`check`、`run` 第一个参数不是规则包名时，就从 arena.json 读规则包并把自己的 bot 排在第一个；`run` 不写对手就补 baseline。回放和日志写到当前目录的 `replays/`，类型检查的临时文件写到系统临时目录。
- `rts-arena view`：用构建好的播放器（`dist/viewer`）起一个只监听本机的服务，读指定目录的回放；静态文件不许跳出播放器目录。
- **对战页**（用户 2026-10-06 要求：不做对战服务，只要本地能自己开比赛）：播放器多一个「对战」页签。它是 `run` 的薄外壳：页面选规则包、每个座位的 bot、分队、局数、种子，服务端（`src/cli/arena-api.ts`，`rts-arena view` 和 Vite 开发服务器共用）用 node 在 bot 目录里执行 `rts-arena run ... --json`，按行读事件给页面显示；回放、每个 bot 的日志、`*.series.json` 汇总都照常写在回放目录。同一时间只跑一场，可以停止。
- **战报**（D-125，`src/cli/report.ts`）：从回放还原整局（局面还原代码 `src/core/replay-model.ts` 和播放器共用），按间隔抽样（默认让整局约 10 行）双方的资源、分数、各类单位和其中闲着的、各类建筑和其中没建好的；关键事件（第一次交火、放地基、建好、失去建筑、第一次挨打、第一次造出某种单位）；战斗（60 tick 内、15 格内的死亡归一场，3 个以上才列）；采集估算（结束时剩的 − 开局的 + 造东西花掉的，造价来自回放新加的 `types[].cost`）和平均囤积；"可能的问题"只写看得出来的事实：bot 停止、报错、被拒最多的命令、平均闲置单位 ≥ 2、平均囤积 ≥ 最便宜造价的 4 倍、没打到过对方建筑、采集不到赢家的 60%、输之前最后一次的单位数对比。`run` 给每个 bot 写的日志开头附上这个 bot 座位视角的战报。D-130 加了换主人事件、事件省略的先后（先合并资源点采完、再只留"第一次……"和换主人，`--full` 全列）、一场战斗最长 300 tick，以及几条提示（同一个位置反复被拆、一场死 3 个以上工人、挨打时还没有兵、第一场大战兵比对手少、工人闲下来之前在做什么）；"兵"是要花钱造、不是工人的单位。
- **多人联赛**（D-128）：`--size K`（默认 2；规则包不能两个人打时是它的最少人数）。赛程：两人局总是全部两两组合；多人局的 K 人组合不超过 20 桌就全打，否则抽 ⌈N×6/K⌉ 桌（`--tables` 可改）——每次从 200 个随机组合里挑上场次数最少、两两碰面最少的，保证每人上场次数最多差 1。每桌打 `--per-table` 局（默认 K），第 g 局座位左移 g mod K 位，每 K 局换一个种子。计分：每局的名次（并列取平均位置）换成名次分 (K − 位置)/(K − 1)，得分率 = 名次分之和 / 局数；"胜"是独得第一、"平"是并列第一；还有平均名次。等级分：每局里每两个人比一次（排在前面算赢、同名次算平），权重 1/(K−1)，这样每人每局一共算一局，再用和两人局同一个带虚拟对手的 Bradley-Terry 算；对阵表是"同一局里排在前面-并列-排在后面"的次数。排名按得分率（抽桌时各人局数可能不同），再看等级分。两人局时这些都退回原来的胜 1 平 0.5、胜平负。分队的规则包也按各自为战打联赛（不分队）。
- **分队联赛**（D-129）：`--teams 2v2`（规则包要支持分队）。轮换搭档（mixed，bot 数够一局的人数时默认）：桌按"一局的总人数"组合（多了抽桌），每桌用 `teamSplits` 列出所有分法（一样大的队不分先后：2v2 有 3 种，3v3 有 10 种，2v2v2 有 15 种），队伍一样大时再轮换各队的位置，一轮 = 分法数 × 队数局（2v2 是 6 局），同一种分法的几次换位置用同一个种子。计分：队伍按名次拿名次分，队里每人拿队伍的分；"胜"是所在队独得第一；等级分只比不同队的两个人，权重 2/(双方的对手人数之和)（队伍一样大时就是 1/对手人数），每人每局一共算一局。搭档表 partners[i][j]：i、j 同队的局数、独得第一的局数、名次分之和。同一个 bot 组队（same）：每队由同一个 bot 的几份副本组成，参赛者就是"队"，桌按队数组合、轮换位置，排名和各自为战一样（日志、统计里这个 bot 的几个座位加在一起算一局）。联赛的页面在规则包支持分队时多出「分队」（只列从大到小的写法，3v1 和 1v3 在联赛里一样）和「搭档」，每桌局数留空 = 一轮。
- **精彩对局**（D-133，`src/cli/highlights.ts`）：每局打完用 `gameFacts` 从回放算看点，只用通用信息（实体造价、生命、死亡、分数），所有规则包都能用。"兵力"是单位和建筑按造价加起来，每约 1/200 局长抽样一次，兵力太少的开局阶段（不到全局最大值的 30%）不算。
  - 逆转：赢家兵力落后、后来又反超（超过 10%）的那段里最低的一刻（只落后不反超的不算，比如到时间按击杀价值赢的）；或者赢家比分落后过（落后还赢了通常是拆了家）。
  - 优势换手：兵力领先的一方换了几次，领先超过 15% 才算。
  - 大战：和战报一样的分法（60 tick、15 格内的死亡算一场，最长 300 tick），死 3 个以上、不是一边倒的场数和最大一场。一边倒（D-164，`isRout`）：只有一方在死人；或者有一方没死兵（只死了工人、建筑）；或者死得少的一方不到死得多的一方的 1/4（按队伍合并，中立算一方）。打掉的比例：打死的造价 / 所有单位和建筑的造价（规则包 remove 的不算），只用来判断没打起来。
  - 两边都伤得重（D-164，替换原来的「打掉的比例」）：各方被打掉的造价 / 自己造过的造价，看损失少的那一方（各自为战时是损失第二多的），到 50% 算满，30% 以上写进看点。
  - 险胜：赢家主建筑（开局生命最大的建筑）最低剩多少血；比分咬得紧只在赢家比分不落后时算。
  - 爆冷：打完按最终排名，赢家一方的平均得分率比最强的对手低多少（差 40 个百分点算满）。
  - 精彩度：逆转 35、优势换手 15、两边都伤得重 15、大战 10、险胜 15、爆冷 20，封顶 100；没打起来（没有大战、打掉不到 5%）−20，平局 −10，有 bot 出错 −30。挑的时候同一组对手最多 2 局，不到 20 分的不要。
  - 结果写进汇总的 `highlights`（`--json` 的 summary 事件里也有），命令行在统计后面打印，对战页放在联赛结果最上面，点「看回放」直接打开。
- **联赛统计**（D-129，`src/cli/league-stats.ts`）：每局从回放算出每个座位的采集（结束时剩的 − 开局的 + 造东西花掉的）、造出的单位、损失的单位和建筑、最后一击打死的敌方单位和拆掉的建筑（中立的也算，自己和盟友的不算），按 bot 累计（同一个 bot 坐几个座位时加在一起），加上回放里的燃料、报错、燃料耗尽、被拒、停止；按座位累计名次分和独得第一；结束原因数字归一后计数。把握度（LOS）用相邻名次的直接对阵（同一局时谁排在前面），近似 Φ((胜−负)/√(胜+负))，平局不算。得分率的 95% 区间用保守估计：名次分在 0～1 之间、方差不超过同样得分率的胜负局，再像 Agresti-Coull 那样加 2 胜 2 负往 50% 收缩（全胜两局时是 ±38%，不会显示成 ±0）。统计每局之后随排名一起更新（`standings` 事件的 `stats`、汇总文件的 `stats`）。D-130：损失的单位另算其中的工人（`lostWorkers`，按回放 types 的 worker 标记）；结束原因每类记下第一局的原话 `example`，显示原话；座位也给得分率的 95% 区间 `ci`（同一个 `rateCi`）。同一个 bot 可以报名多次，名字带 #编号。
- **联赛**（D-127，`src/cli/league.ts`、`cmdLeague`）：2～16 个 bot、规则包要能两个人打；所有两两组合，每对打 `--per-pair` 局（默认 2），同一对的第 2k、2k+1 局用同一个种子换边；先把每对的第 1 局都打完再打第 2 局，中途停下时各对打的局数差不多。排名：胜 1 分、平 0.5 分，同分看等级分。等级分用 Bradley-Terry 模型的 MM 迭代从全部对局一起算（和先后顺序无关，不像逐局更新的 Elo），每个 bot 先送一胜一负给一个强度固定为 1（1500 分）的虚拟对手，全胜、全败也是有限的分数，换算成 1500 + 400·log10(强度)。每局照常写回放和每个 bot 的日志；汇总写成 `kind: "league"` 的 `*.series.json`，每局更新 `standings`，对战页的历史记录读它。`--json` 时每局之后多一个 `standings` 事件，对战页接口只留最新的一份（不然长联赛会把事件数撑满）。对战页选「联赛」后座位数不按规则包、可加到 16 个，「局数」变成「每对局数」，实时显示排行榜和对阵表，每一局折叠起来。
- **选 bot**（D-124，`src/cli/bot-finder.ts`）：`/api/arena` 返回找到的 bot 文件——bot 目录本身和子文件夹（最深 3 层，跳过 node_modules、replays、dist、out、点开头的目录、规则包目录，以及平台仓库里的 src、test、viewer、bots、rulesets），bot 目录本身有 arena.json 时再加上一层里的其他 bot 目录（start.bat 那样 my-bot、my-bot2 并排）。导出了 `onTick` 的 .ts 才算 bot。每个文件归到最近的 bot 目录，标上那个目录用的规则包；这些 bot 目录用到的自己写的规则包也加进规则包列表（id 是相对路径），开比赛时只接受列表里有的规则包。浏览器不告诉网页本地文件的路径，所以「从电脑选文件…」把内容 POST 给服务端，存成 `<回放目录>/uploaded-bots/<名字>.ts`（最多 50 万字，必须导出 onTick），之后也出现在列表里（只显示名字）。名字是选完文件后在页面上起的（用户要求：不然认不出是谁写的 bot），比赛结果、排行榜、日志文件名里都显示它；只能用字母、汉字、数字、_、-，1～40 个字，不能叫 bot（显示时 bot.ts 会换成所在目录名）。同名时内容一样就直接用，内容不一样返回 409，页面问"替换成新上传的"（同一个作者更新 bot）还是"换个名字"。`/api/arena/upload/rename` 给上传的副本改名（只能改 uploaded-bots 里的，新名字被占了返回 409），以前的回放里还是旧名字。`/api/arena/upload/delete` 删除上传的副本（用户要求）：只能删 uploaded-bots 里的；正在跑的比赛参数里有它时返回 409（联赛每局都重新读 bot 文件，中途删掉后面的局会出错）；页面上先确认，用着它的座位换回默认 bot。每个规则包上次开比赛的阵容记在浏览器的 localStorage，找不到了的换回默认。写操作要带 `X-Arena` 请求头（别的网站借浏览器发不了带自定义头的跨站请求），参数不经过 shell 传给命令行。
- **一键脚本**（D-118）：`start.bat` 检查 Node.js（23.6 以上）和 Git，缺了就用浏览器打开官网下载页；平台文件夹是脚本所在目录（压缩包解压或克隆的），否则克隆到脚本旁边的 `rts-arena`；没装依赖或没构建播放器就 `npm ci`（默认源失败换 npmmirror 再试）；没有 `rts-arena` 命令就 `npm install -g .`；没有 `my-bot/arena.json` 就 `init annihilation my-bot`；最后在 my-bot 里 `view --open`。`view --open` 发现端口上已经是播放器就只打开浏览器（重复双击不报错）。`update.bat` 先确认播放器没开着（重装依赖会让它出错），压缩包装的平台第一次更新时 `git init` 接上仓库并换成最新版，之后 `git pull --ff-only`、`npm ci`、在 my-bot 里 `init` 刷新说明书。用 `npm ci` 而不是 `npm install`，免得改动 package-lock.json 让下次 pull 失败。批处理文件用 UTF-8 + `chcp 65001`，仓库里也存 CRLF（`.gitattributes` 里 `*.bat -text`）：cmd 读 LF 结尾的 UTF-8 批处理会错位，单独下载 start.bat 时拿到的是仓库里的原始字节。
- 依赖：运行时只要 quickjs-emscripten（锁定 0.32.0，沙箱依赖它的内存行为）和 typescript；Vite、PixiJS 只在构建时用。

## 13. 建造（D-119、D-120）

用户 2026-10-06 要求：工人能造兵营，再做一个支持建造的模式。

- 接口：`TypeSpec.builds`（单位能建的建筑类型，内核检查都是建筑）、命令 `build(unit, type, x, y)`、命令状态 `{ kind: "build", target }`、实体字段 `construction: { done, total }`、事件 `built`、`Game.fog`、全局函数 `canBuild`。建筑的 `buildTicks` 兼作建造工作量。
- 地基在命令被接受时立即放下、立即扣钱（和 produce 一样"下命令就扣"，bot 好记账），之后没有"失败、退款"的中间状态。另一种做法是工人走到了再放地基（星际那样），要处理走到了钱不够、位置被占的失败和退款，状态多，没选。
- 占地的每一格都要在己方队伍视野里，否则"被占"的拒绝能拿来探测迷雾里有没有东西。检查顺序：超出地图 → 地形和资源点 → 视野 → 其他实体。地形和资源点整局都看得见，先查它们不泄露什么；原来是先查视野，看不见的岩石也只说"不在视野里"，bot 要派人过去才知道那里根本不能建（D-130 改）。
- 占地上有单位（包括建造者自己）就拒绝，不推开单位。bot 看到的局面和命令执行时的位置完全一样（命令在下一 tick 结算前执行），所以 `canBuild` 的判断是准的。
- 工人贴着地基（距离 1）时每 tick 干 1 份活，多人叠加；走路用到地基的流场（和采集一样）。建造阶段放在移动之后、采集之前。对自己没建好的同类地基（左上角相同）下 `build` 就是去帮忙，不扣钱。
- 地基生命从 1/10 起按进度涨，建造期间挨的打不补（打地基比打建好的划算）。没建好的建筑不能生产、交货、攻击，但挡路、能被打。
- 对没建好的建筑 `cancel` 是拆掉、退 75%：不全额退，免得放地基当免费路障再收回来。
- 规则包事件多了 `built`，`died` 带 `unfinished`，规则包可以按建好没建好给不同的击杀价值。回放帧多了建造进度 `bp`，播放器把没建好的建筑画淡、底边画蓝色进度条。
- 现有四个规则包的工人没有 `builds`，行为不变（单位表只在有能建造的单位时才多出「能建造」一列）。

**拓荒**（`rulesets/frontier`）：56×40，开局主基地 + 5 个工人 + 300 金、没有兵营；可以建兵营（150 金，工作量 240）、箭塔（100 金，工作量 200，450 血，伤害 12 / 射程 5 / 冷却 10，比弓手远 1 格）、仓库（100 金，工作量 150，交货点）。家门口 4 个矿，绕过石墙 3 个分矿（离家远，适合建仓库），地图中间一带 4 个大矿（每边离得近一点的各 2 个）。摧毁主基地获胜；到 9000 tick 比击杀价值（建好的兵营、箭塔、仓库按造价 2 倍，地基按造价）。每次燃料 130：整局 1800 次调用，正好在建议的整局 24 万以内。

基准 bot：兵营 → 箭塔 → 仓库（派一个工人去分矿，走到看得见的地方再放）→ 分矿箭塔 → 第二座兵营。放地基时避开建筑和金矿四周一格、以及金矿到交货点之间的矩形（不堵采矿的路）；计划要建但钱不够时把钱预留下来，生产只花预留之外的钱——不预留的话兵营每次都把钱花光，箭塔永远攒不出来。对不动的对手约 1800 tick 获胜；对速攻示例 `rush`（5 个工人一起建兵营、只出战士、4 个一波）6 局全胜；镜像 6 局 3:3，都在 2300～3200 tick 分出胜负。

## 14. 规则包沙箱（D-122、D-123）

用户 2026-10-06 要求。目的是让大模型、别人写的规则包也能放心跑；随后用户要求自带的规则包也统一进沙箱（D-123），现在命令行和对战页加载的所有规则包都在沙箱里跑。不经过沙箱的 `importRuleset` 只留给测试（比较两种跑法）和调数值的开发脚本。

- **引用方式**：规则包参数写名字是平台自带的（`rulesets/<id>/`），写路径（带斜杠或以 `.` 开头）是规则包目录。bot 目录的 `arena.json` 里存相对 bot 目录的路径；现成 bot 在规则包目录的 `bots/`。外部规则包的 id 不能和自带的重名（回放文件名、对战页都按 id）。
- **运行方式**（`src/sandbox/ruleset.ts`）：每个加载好的规则包一个独立的 WebAssembly 实例（内存上限 256 MB），每局在 setup 时新开一个 QuickJS 上下文重新执行规则包代码（顶层变量里的状态不会带到下一局），一局结束 `release`。加载时先在一个临时上下文里读出静态数据（参数、地形、类型），用 `rules-check.ts` 逐项检查，格式不对一次列出所有问题。
- **导入**：模块解析器只认 `./`、`../` 开头（解析后必须还在规则包目录里）和 `"rts-arena/standard"`；`import type` 在擦类型时就没了。QuickJS 的解析器失败时不会把原因带给加载器（加载器拿到空名字），所以解析器返回一个带前缀的假名字，由加载器报告原因。
- **ctx 桥接**（`rules-prelude.ts`）：沙箱里的 ctx 是 prelude 搭的。读操作向宿主要 JSON 快照，同一 tick 的 onTick、result 和下一轮的 objectives 共用一份（内核在这几次调用之间不动局面），规则包自己刷实体、移除时作废重取；加分、改资源、出局在缓存里同步改，所以和直接拿内核对象时读到的一样。写操作是宿主函数，每个都检查参数（玩家编号、整数、字符串长度），setTerrain、spawn、setResources 只能在 setup 里用，setTerrain 只能调一次。`ctx.rng` 每次向宿主取数，和直接跑是同一串随机数。快照里和默认值一样的字段不传（宽高、储量、idle、空队列……），沙箱里补全，传输量少一半左右。
- **上限**：燃料（加载 2000、setup 4000、onTick 和 result 每次 400、objectives 100、timeUp 1000）、单次墙钟 2 秒（加载、setup 10 秒）、整局 120 秒、栈 256 KB；硬上限地图边长 256、8 人、5000 个实体、64 种类型、bot 燃料每次 2000；叠加层、状态文字、objectives 的大小也有上限。超了就是规则包出错：抛错、这一局作废，报错里写明哪个回调、第几 tick（`run` 停下并报告，`check` 列出来）。规则包的 `console.log` 打到标准错误。
- **结果一样**：`test/rules-sandbox.test.ts` 把五个自带规则包放进沙箱，和直接跑的回放逐字节比较（基准 bot 对打 1200 tick；混战三家里两家出局、实体被清掉），完全一致。同一个文件里还测了越界 import、死循环、内存超限、setup 以外改地形、参数不对、实体数超限、定义格式不对、返回值不对、用 Date 等情况都能拦住并说清原因。
- **速度**：沙箱里的规则包慢在把实体快照传进 QuickJS 再解析（它是解释器）。一开始每次回调都重取全部实体时是直接跑的 6 倍；改成同一 tick 共用一份、省掉默认字段后是 2～3 倍；再给 `ctx.entities` 加筛选（`{ owner, type, kind }`，没取过全量快照时由宿主筛好只传结果，`entitiesIn` 同理），自带规则包每 tick 找主基地改用筛选后，整局（含 bot）是直接跑的 1.5～1.9 倍：koth 1422 tick 0.41 → 0.74 秒，annihilation 2131 tick 0.42 → 0.77 秒，melee 3000 tick 0.73 → 1.35 秒，frontier 2646 tick 0.79 → 1.18 秒，harvest 1375 tick 0.28 → 0.42 秒。
- **写规则包**：`rts-arena new-rules <目录>` 建一个能直接跑的示例规则包（采金赛：先交够 600 金），带基准 bot、写法说明 `RULESET.md`（`src/api/RULESET.md` 的副本）和给编辑器用的 tsconfig（`paths` 把 `rts-arena/ruleset`、`rts-arena/standard` 指到这台机器上平台的文件）。`rts-arena check <规则包>`：规则包的类型检查、加载、说明书能否生成、`bots/` 里的 bot 过类型检查、每种人数（支持分队再加 2v2）试打、用不动的 bot 打一整局看结束判定。对战页也会列出 bot 目录 `arena.json` 里写的外部规则包（标"沙箱"），开比赛时只接受自带规则包和这一个路径。

## 15. 已知风险

- 大地图上 bot 让很多单位各自去不同的格，流场缓存会被打穿、每 tick 重复做 BFS；这部分耗时不计入 bot 燃料，写得差的 bot 能把一局拖慢（引擎审阅员推测，未实测）。
- 墙钟超时（单次、整局累计）和机器快慢有关，不可复现，只当兜底。
- `canBuild` 要遍历全部看得见的实体，bot 在大片区域里逐格调用会很费燃料；基准 bot 先用自己的占用格筛选，只在要建的时候找，单次燃料最高 1。

## 18. 随机地图（D-141）

用户 2026-10-07 要求，"注意不要影响两边平衡"。起因：做联赛视频时看到 60 局联赛里同一对阵几乎每局结果一样（19:1、20:0），bot 的注释写着"数值都是用回放数据调出来的"——地图固定，bot 就会对着这一张图调参数、写死路线，联赛里同样的对手打再多局也没多少信息。

**做法**：`rulesets/common/standard.ts` 加 `randomSymmetricMap(ctx.rng, spec)`（自己写的规则包从 `"rts-arena/standard"` 也能用）：

- 输入：底图（固定的特殊地形先画好）、要留空的区域（`keepClear`）、开局就占着格子的东西（`solid`）、随机障碍的块数 / 形状 / 地形字符、随机矿群（锚点范围 + 阵型）、必须走得通的点（`connect`，第一个是自家门口）。
- 生成：先放矿群（所有对称位置都要在空地上、不在保留区，不同对称位置之间至少隔两格），再成套放障碍（不压保留区、不和已有障碍重叠）；两人图中心对称、正方形多人图转 90° 四重对称，每家看到的地图完全一样。
- 校验（四方向，和引擎寻路一样）：自家门口能走到所有 connect 点和它们的对称位置、能走到每个矿的旁边，最短路不超过曼哈顿距离的 1.5 倍再加 6 格；能走的格子至少 75%。不合格就换一组重来，200 次都不行返回 null，规则包用自己的经典布局（就是 D-141 之前的固定地图）。只用 `ctx.rng`，同一个种子永远是同一张图（沙箱和直接跑一样）。

**各规则包固定 / 随机的部分**（固定的是玩法核心，随机的是地形和一部分争夺矿）：

| 规则包 | 固定 | 随机 |
|---|---|---|
| 歼灭、夺点、采集竞速 | 家（主基地、兵营、开局工人、家门口 4 个矿）；夺点的控制点 | 墙、水；中间的争夺矿群 |
| 拓荒 | 家、分矿和隔开分矿的那道墙 | 别的墙、水；地图中间那对大金矿 |
| 烽火台 | 家、5 个台址、矿和野怪；中央两侧两道收口横墙（见下） | 别的墙、水 |
| 混战 | 各角的家、家门口的矿、正中的矿群 | 墙、水；两家之间那对矿 |
| 劫镖 | 家、四条商路 | 石头、水塘；四条边中间那对矿 |
| 夺旗 | 家、旗台广场、高地、巨魔路点 | 墙、水 |
| 牧野争牛 | 家、牧场、荒原和狼穴 | 荒原外的墙、水 |

障碍块数按经典图的密度调过：200 个种子平均的障碍格子数和经典图基本一样（歼灭 136 / 经典 144，混战 206 / 208……）。每个规则包 300 个种子生成 300 张不同的图，没有一次退回经典布局；生成一张图不到 1 毫秒。两家门口之间的最短路，经典图和随机图都等于（或几乎等于）曼哈顿距离——四方向移动时墙很少挡住"单调"的路线——所以速攻的路程不变。

**平衡验证**：9 个规则包各用全部参考 bot 打联赛（两两每对 8 局，同一个种子换座位各打一次，起始种子 1000），随机地图一遍、同样的种子在经典地图上一遍（临时让生成器返回 null）。

- 两边平衡：P0 座位的总得分率，经典 48.8%、随机 47.6%（各 432 局，95% 区间约 ±4.7%），都盖住 50%，两者也几乎一样。单个规则包里看到的 44%～56% 在经典图上同样有，是局数少的误差，不是随机地图带来的。对称加上换座位，地图本身不会偏向哪一边。
- 打法平衡：多数规则包参考 bot 的强弱顺序不变（歼灭 baseline 92→100、llm 71→67、rush 29→29、boom 8→4；夺点 steady 93→88、baseline 68→73……；拓荒 expand 92→88、turtle 63→67、baseline 46→42、rush 0→4；数字是经典→随机的得分率）。变化大一点的：采集竞速 raider 50→69、夺旗 raider 58→38 / sneak 0→17、混战两人局 baseline 和 boom 换了位置（每对只有 8 局，误差约 ±19%）。
- 烽火台出了问题：随机地图上 rush 从 38% 涨到 69%。原因是经典图中央两侧的两道横墙把两家之间的近路收到中央、从两个守卫身边过（守卫不动，贴身打 12 点），速攻先要挨守卫的打；随机地图拿掉了这两道墙。把它们固定下来以后 rush 56%、baseline 50%、hunter 44%（每对 16 局）；同样种子的经典图 baseline 66%、rush 44%、hunter 41%，差在误差内。中央上下的两个水塘也试着固定过，rush 不变，就没固定。
- 这说明随机化时要先想清楚哪些地形是"玩法的一部分"：拓荒隔开分矿的墙、烽火台的收口墙属于玩法，夺点的控制点要留空，商路不能挡。新规则包用 `randomSymmetricMap` 时同样要把这类地形放进底图。
- 参考 bot 没有因为地图变化报错或卡住（报错、燃料耗尽、被拒命令、停止的总数和经典图一样，烽火台的两次被拒是双方抢着在同一格建烽火台）。只有烽火台 baseline 写死了一个集结点坐标 (13, 8)，它挨着固定的矿，不受影响。

**给写 bot 的人**：说明书「开局地图」一节会比较几个种子的开局，写明"地图每局按种子随机生成"、哪些每局一样（各家开局的建筑和单位、家门口的资源点）、哪些每局不同（其余资源点、墙和水），提醒别把坐标写死；`rts-arena map <规则包> --seed N` 画出任意种子的地图；`rts-arena check` 每个位置用不同的种子试打（原来都是种子 1，等于只在一张图上试）。规则包的 RULES.md 也写了地图每局随机。

**给写规则包的人**：RULESET.md 推荐地图每局随机，说明 `randomSymmetricMap` 怎么用；`new-rules` 的模板改成随机地图（家固定，墙、水和中间的大金矿随机）。

## 19. 局中改数值和科技规则包（D-153、D-154）

扩展分三档（用户先定做第 1 档）：

| 档 | 内容 | 状态 |
|---|---|---|
| 1 | 规则包局中改单位数值（`setTypeStats` / `setStats`） | 已做（D-153），配「科技」规则包验证（D-154） |
| 2 | 规则包自定义命令：bot 发起、规则包结算（研究、技能、驻军、交易） | 没做，会改 D-003 |
| 3 | 多格单位、斜向移动、弹道、连续坐标 | 不做（和格子 + 曼哈顿距离冲突） |

**第 1 档怎么实现的**：内核读单位数值一律走实体的 `e.def`，所以"改数值"就是给实体换一份有效定义：原值 → 叠上"这个玩家这类实体"的改动 → 再叠上"这个实体"的改动。改动按"改成多少"合并（不是加减），写原值或 null 就改回去；合并后和原值一样就用回原来那一份（没改过的实体不多占内存，也让判断"改过没有"只要比对象）。生命上限变化时当前生命跟着调；换主人时按新主人的改动重算。几处同步的地方：

- bot：`view.entities[i].stats` 列和 `game.types` 不一样的项（生命上限已经在 `maxHp`）；沙箱里 `canBuild` 判视野也看它。
- 回放：实体快照 `st`、帧里 `st: [id, 改过的项 | null]`；播放器的视野、血条、选中信息，视频的血条都按它；测试逐 tick 比对 bot 看到的实体和播放器算出来的一样（改了视野也一样）。
- 规则包沙箱：实体快照里改过的带上 `def`，沙箱里不按类型补；沙箱和直接跑的回放逐字节一致（测试用科技规则包打一局真的攀了科技的）。
- 拓荒的代码抽到 `rulesets/common/frontier.ts` 后，拓荒的回放和抽之前逐帧一致。

**科技规则包的设计**：科技是建筑而不是"研究"，因为第 1 档没有新命令，玩家只能用已有的 build 选科技；"建筑在加成在"顺带让科技建筑成了值得去拆的目标。四种科技各管一样（伤害、生命、射程、经济），参考 bot 覆盖四种思路。实验：同一个 bot 带不带科技 12:8、开分矿的带不带科技 13:7，说明科技值得攀但不是一边倒；只攀科技、兵出得晚（scholar 第一版先建矿业所和铁匠铺再建箭塔）会被速攻和开分矿打穿（0:12），改成先站稳再攀才有 17:13。

## 20. 兵种克制（D-166）

**平台**：单位定义的攻击加一个可选的 `vs: { 类型: 倍数 }`，打这些类型时伤害 = damage × 倍数（四舍五入），倍数 0～10、可以是小数。只改了战斗结算一处（`damageOf`），`damaged` 事件记实际伤害；bot 从 `game.types` 看到倍数，说明书单位表写「打 cavalry ×3」，视频图例写「克骑兵」（放在射程前面，图例排两栏截断时先留住它；图例改成一栏放得下就排一栏）。自动攻击不看克制，还是挑最近的：让兵专打被自己克的是 bot 该做的事。倍数不能局中改（`setTypeStats` 改的 damage 照样乘倍数）。

**三种兵**（`rulesets/common/counter.ts`）：

| 兵 | 造价 | 生产 | 生命 | 走一格 | 攻击 | 克制 |
|---|---|---|---|---|---|---|
| 枪兵 | 75（D-169 前是 70） | 60 tick | 130 | 3 | 9 / 1 / 8 | 打骑兵 ×3 |
| 骑兵 | 105（D-170 前是 100） | 70 tick | 170 | 2 | 12 / 1 / 8 | 打弓兵 ×2.5 |
| 弓兵 | 75 | 60 tick | 60 | 3 | 9 / 4 / 8 | 打枪兵 ×2.5 |

数值实验（歼灭地图，歼灭基准 bot 只改出兵顺序，每组 20 局）：纯枪兵对纯骑兵、纯骑兵对纯弓兵、纯弓兵对纯枪兵都是 20:0；三兵种混编对任何纯兵种 20:0；两兵种搭配之间也成环：枪骑 17:3 骑弓、骑弓 18:2 枪弓、枪弓 20:0 枪骑；骑弓对三兵种混编 15:5、枪弓 9:11、枪骑 4:16。克制关系对称，三兵种平均出就没有弱点，要赢它得靠经济、时机和挑目标。

**克制歼灭的参考 bot**（每对 20 局）：baseline 71%（三种轮流）、counter 69%（第 300 tick 派工人到对方主基地前侦察，按看到的敌方兵折成克它们的兵来配）、boom 54%（counter 的出兵加 15 个工人、14 个兵再出击）、rush 31%（纯骑兵突袭，19:1 赢骑射）、mobile 25%（骑兵弓兵 1:1）。counter 不侦察时只有 9:11 赢 mobile：头一波 10 个兵出完前还没见过对方的兵，第一仗是按平均配比打的；加了侦察 16:4。基准 bot 挑目标改成"打几下能打死"优先（自然先打被自己克的），实验里只改出兵的骑弓能 15:5 赢混编，换成这种挑法后只有 8:12。

**克制拓荒的参考 bot**（每对 10 局）：expand 75%（开分矿，弓兵为主）、turtle 65%（箭塔守家，枪兵为主）、baseline 48%、counter 48%、rush 15%（两座兵营的纯骑兵速攻）。一开始 expand、turtle 也是三种平均出，expand 89% 通吃、速攻 5%；改成各有偏重的配比以后速攻对 expand 5:5。速攻试过纯枪兵、枪枪骑、枪弓、骑弓、三种平均，对 expand、baseline、turtle、counter 都赢不到三成：防守方的混编里总有克它的兵，加上箭塔，单一兵种早冲在克制规则下吃亏，这是规则本身的性质，保留纯骑兵速攻当"怕枪兵"的陪练。counter 输 turtle 3:7 主要是攻进箭塔群、到时间比击杀价值输，不是配比问题。

**侦察兵（D-167）**：克制要看情报，迷雾下对手出什么兵只能靠看到。试写的 bot 派工人去侦察反而更差（少一份采矿，首战兵少 1～2 个），用户定开局送一个专门侦察的单位：走一格 1 tick（全场最快，骑兵 2 tick）、视野 8（比箭塔射程 5 远）、25 血、攻击 1，造不出来。参考 bot 联赛（侦察兵在角落）：克制歼灭 counter 73%（用侦察兵，排第一）、boom 64%、baseline 63%、mobile 29%、rush 23%；克制拓荒 turtle 68%、expand 65%、counter 57%、baseline 45%、rush 15%。两个试写 bot 收为 `llm`，加了侦察兵以后对其余参考 bot 仍是每个 10 战全胜。
