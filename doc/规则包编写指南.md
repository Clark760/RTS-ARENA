# 规则包编写指南

规则包就是一种玩法。这份指南从平台自带的示例规则包讲起，再带你动手加一个新机制、调到好玩，最后讲怎么设计和发布。每个接口的完整说明在 `RULESET.md` 里（`rts-arena new-rules` 会复制一份到你的规则包目录），这里讲思路和做法。先熟悉一下自带的玩法会很有帮助，见 [规则包介绍](规则包介绍.md)。

## 1. 规则包管什么，平台管什么

| 规则包定 | 平台负责 |
|---|---|
| 地图和地形、开局摆什么 | 移动和寻路、战斗、采集、生产、建造 |
| 有哪些单位和建筑、数值多少 | 视野和战争迷雾 |
| 怎么计分、怎么判胜负、时间上限 | 运行 bot 的沙箱（燃料、内存、出错处理） |
| 中立单位做什么（野怪、商队……） | 回放、播放器、战报、联赛、视频 |
| 给 bot 看的目标信息、玩法说明 | 说明书 `PROMPT.md` 和接口 `arena.d.ts` 的生成 |

所以写规则包不用管单位怎么走、怎么打，只要定好"这局玩什么"。目前有这些边界：

- bot 能下的命令是固定的（走、打、边走边打、采集、停、生产、取消、建造），规则包不能加新命令；
- 单位都是 1×1，地图是格子，距离按曼哈顿距离算。

在这些边界里能做的已经很多：中立单位、占领和换主人、局中改单位数值（科技、增益）、限制建筑放在哪、自己的事件和统计。自带的 12 个规则包都是这么写出来的。

## 2. 从模板开始

```bash
rts-arena new-rules my-rules
```

建好一个能直接跑的示例规则包「采金赛」：先累计交够 600 金的赢，拆掉对方主基地也直接赢。目录里有：

| 文件 | 是什么 |
|---|---|
| `index.ts` | 规则包本身：参数、单位、开局、计分、胜负 |
| `objectives.ts` | `view.objectives` 的类型，bot 作者拿到的接口里会原样出现 |
| `RULES.md` | 给 bot 作者看的玩法说明，会放进 `PROMPT.md` |
| `bots/` | 参考 bot：`baseline`（均衡）、`rush`（速攻）、`greedy`（只采不打） |
| `RULESET.md` | 完整的写法说明（平台提供） |
| `api/` | 平台接口的只读副本，查字段和函数签名看这里 |

先检查一遍。命令里的规则包要写成路径（带 `./`），不然会被当成平台自带规则包的名字：

```bash
rts-arena check ./my-rules
```

```
规则包类型检查通过
在沙箱里加载通过：「采金赛」（my-rules），2～2 人
说明书（PROMPT.md、arena.d.ts）能生成
现成 bot 类型检查通过：baseline、greedy、rush、idle
2 人（P0 是 baseline、其余不动）试打 300 tick 通过，用时 0.1 秒，实体峰值 20，baseline 被拒命令 0
整局（P0 是 baseline、其余不动）：第 768 tick 结束，赢家 P0——先交够 600 金（用时 0.3 秒）
整局（P1 是 baseline、其余不动）：第 786 tick 结束，赢家 P1——先交够 600 金（用时 0.3 秒）
整局（全是 baseline）：第 803 tick 结束，赢家 P1——先交够 600 金（用时 0.4 秒）
规则包检查通过
```

再让三个参考 bot 循环对打：

```bash
rts-arena league ./my-rules baseline rush greedy --per-pair 10
```

模板的结果是只采不打的 `greedy` 19 胜 1 负，`baseline` 55%，`rush` 全败。这说明「采金赛」纯拼经济，出兵不划算。下面第 4 节就用一个新机制来改变这一点。

## 3. 读懂模板

打开 `index.ts`，从上到下是这几块。

**基本参数**

```ts
id: "my-rules",            // 小写字母开头，不能和自带的重名
name: "采金赛",
summary: "先累计交够 600 金的赢，摧毁对方主基地也直接赢",   // rts-arena list 里显示的一句话
players: { min: 2, max: 2 },
maxTicks: 4000,            // 一局最长（1 秒 = 10 tick）
decisionInterval: 5,       // 每 5 tick 调一次 bot
fuel: 100,                 // bot 每次调用的燃料上限
unitCap: 30,               // 每人单位上限
fog: true,                 // 战争迷雾
```

**单位**（`types`）：`standardTypes()` 是平台的标准单位（主基地、兵营、工人、战士、弓手、金矿），可以直接用，也可以在它上面改数值、加新类型。每种类型的 `look` 决定回放里怎么画：形状、图形上的一个字、颜色，`name` 是中文名，视频的单位图例里用。

**开局**（`setup`）：

1. `randomSymmetricMap` 按种子生成一张对称的随机地图：家固定，墙、水和中间金矿的位置每局换；
2. `setTerrain` 铺地形；
3. `spawnMirrored` 在两边对称地摆主基地、兵营、工人、金矿；
4. `setResources` 给开局的钱。

地图每局随机很重要：地图固定的话，bot 会对着这一张图调参数、写死路线，换张图就不行。

**每 tick**（`onTick`）：内核把这一 tick 的移动、战斗、采集都结算完后调用。模板在这里读本 tick 的事件，工人每交一次货就给交货的玩家加分，再用 `setStatus` 更新回放顶部的状态栏。

**给 bot 的信息**（`objectives`）：返回 bot 在 `view.objectives` 里看到的东西，比如目标分数、双方分数、对手主基地的位置。返回值的结构要和 `objectives.ts` 里写的类型一致。

**判胜负**（`result` 每 tick 调一次，`timeUp` 到时间上限时调用）：返回 `{ winner, reason }`；`result` 返回 `null` 表示还没分出胜负。

**`RULES.md`**：bot 作者靠它了解玩法。数字照实写，`view.objectives` 的每个字段都要说明。

## 4. 动手：给中间的大金矿加守卫

目标：中间的大金矿（800 金）旁边站一只中立守卫，不清掉它就没法安心采矿；打死它的玩家得 100 金。这样只采不打就不行了。下面每一步的代码都在模板上实际跑过。

### 第 1 步：加一种单位

在标准单位上加一个守卫。要给 `types` 标上类型，不然 `kind: "unit"` 会被推断成普通字符串：

```ts
import type { RuleContext, Ruleset, TypeSpec } from "rts-arena/ruleset"

const BOUNTY = 100
// 在标准单位上加一个中立守卫：不会动，只打贴身的单位
const types: Record<string, TypeSpec> = {
  ...standardTypes(),
  guardian: {
    kind: "unit",
    maxHp: 300,
    moveTicks: 0,
    sight: 3,
    attack: { damage: 12, range: 1, cooldown: 10 },
    look: { shape: "triangle", label: "守", color: "#8b4513", name: "守卫" },
  },
}
```

`moveTicks: 0` 表示不会动。中立单位（owner 是 -1）闲着时会自动打贴着它的玩家单位；玩家的单位不会自动打中立单位，要 bot 下 `attack` 命令。

### 第 2 步：开局放守卫

在 `setup` 里、给开局的钱之前，给每个中间大金矿旁边放一只：

```ts
// 每个中间大金矿（800）旁边放一只守卫；spawnNear 从金矿外圈找空格
for (const m of ctx.entities({ type: "goldmine" })) if (m.amount === 800) ctx.spawnNear("guardian", -1, m.x, m.y)
```

`spawnNear` 会自己找空格，不用记哪些格子被占了。

### 第 3 步：赏金和战况

在 `onTick` 里读死亡事件：`killer` 是最后一击的玩家（-1 表示没有）。给赏金，再用 `note` 往回放的战况和战报里写一条：

```ts
// 打死守卫的赏金：killer 是最后一击的玩家
for (const ev of ctx.events)
  if (ev.kind === "died" && ev.type === "guardian" && ev.killer >= 0) {
    ctx.addResource(ev.killer, "gold", BOUNTY)
    ctx.note(`P${ev.killer} 打死了守卫，得 ${BOUNTY} 金`, ev.killer)
  }
```

### 第 4 步：写进 RULES.md

bot 作者只看说明书，没写的事他们不会知道。在 `RULES.md` 里加一段：

```
**守卫**：每个中间大金矿旁边站着一只中立守卫（`guardian`，生命 300，伤害 12，射程 1，冷却 10）。它不会动，但会打贴着它的单位（不分是谁的），所以去中间采矿前要先清掉它。你的单位不会自动打它，要用 `cmd.attack` 点名打。最后一击打死守卫的玩家得 100 金。
```

### 第 5 步：改参考 bot

玩法变了，参考 bot 也要跟着变，不然它们根本不会用新机制。给 `baseline` 加两行，凑够 3 个战士先去打离家最近的守卫：

```ts
// 看得见的守卫里离家最近的那只：凑够 3 个战士先去打它（守卫不会动，打死有赏金，中间的大金矿才能采）
const guard = nearest(base, view.entities.filter((e) => e.type === "guardian"))
for (const s of soldiers) {
  if (threat) cmd.attack(s, threat)
  else if (guard && soldiers.length >= 3 && dist(guard, base) <= 16) cmd.attack(s, guard)
  // ……后面照旧
}
```

第一行的打法说明也一起改，`PROMPT.md` 里的参考 bot 表就是读这一行。

### 第 6 步：检查、对打，看机制有没有起作用

```bash
rts-arena check ./my-rules
```

```bash
rts-arena league ./my-rules baseline rush greedy --per-pair 10
```

我实际跑出来是这样的：

| 改动 | greedy（只采不打） | baseline | rush（速攻） | 怎么结束的 |
|---|---|---|---|---|
| 模板原样，目标 600 | 95% | 55% | 0% | 都是交够金子 |
| 加了守卫，目标还是 600 | 100% | 50% | 0% | 都是交够金子 |
| 目标改成 1200 | 0% | 70% | 80% | 30 局里 29 局拆家 |
| 目标改成 900 | 5% | 75% | 70% | 16 局交够金子，14 局拆家 |

- **加了守卫，结果却没变**：600 金靠家门口两个矿（一共 800）就够了，没人需要去中间，守卫等于摆设。**加了机制一定要用联赛确认它真的起了作用。**
- **目标改成 1200**：家门口的矿不够了，必须去中间，守卫起作用了。但又走到了另一头：几乎每局都是拆家结束，采金变成了陪衬。
- **目标改成 900**：两条赢法都走得通，这才像样。`greedy` 还是很弱，因为它不出兵，挡不住守卫和速攻，这是这个打法本身的问题。

想确认机制到底发生了多少次，可以在结果里带上**自己的统计**。在顶层记数，结束时放进 `result` / `timeUp` 的返回值：

```ts
/** 每个玩家打死了几只守卫（每局重新加载，不用清零），结束时放进结果的 stats */
const guardKills = [0, 0]
const withStats = <T extends object>(r: T) => ({ ...r, stats: { 打死守卫: [...guardKills] } })
// onTick 里打死守卫时：guardKills[ev.killer]++
// result、timeUp 里：return withStats({ winner: ..., reason: "..." })
```

联赛最后会多出一张表，按 bot 列出每局平均打死了几只守卫（这次 baseline 约 0.7～0.8 只，另两个是 0）；战报里也会列出来。

## 5. 怎么设计一个好玩法

- **每种打法都该有胜有负**：参考 bot 联赛里某种打法全胜或全败，往往是玩法有问题，不一定是 bot 写得不好。
- **至少 3 个打法不同的参考 bot**：速攻、先发展、守家、专打你的新机制……只有一个基准 bot 时，写 bot 的人只会对着它调。每个文件的第一行写一句打法说明。
- **地图每局随机、两边对称**：用 `randomSymmetricMap`，然后看联赛统计里的「座位」那一行，两边得分率的区间都盖住 50% 才说明不偏。
- **能在时间内分出胜负**：看联赛统计里的「结束原因」和「打到时间上限才结束的对局」。几种结束方式都出现，玩法通常更有意思。
- **给 bot 足够的信息**：关键位置、当前状态都放进 `objectives`。比如限制了建筑只能放在某些地方，就把能放的位置列出来，不然每个 bot 都得自己把你的规则重算一遍。
- **说明书写清楚**：数字照实写；中立单位会做什么、"你的单位不会自动打它"这类反直觉的地方要专门提醒。
- **回放和视频好看**：新类型都写 `look.name`（中文名）；用 `setMarkers` 画出区域（控制点、台址这类）；用 `setStatus` 显示比分；关键时刻用 `note` 写进战况。
- **编号从 P0 起**：状态文字、战况里写玩家用 P0、P1，和平台的输出对得上。

## 6. 常用接口

| 什么时候 | 接口 |
|---|---|
| 只能在 `setup` 里 | `setTerrain(rows)`、`spawn(type, owner, x, y)`、`setResources(player, { gold })` |
| 读局面 | `entities({ owner, type, kind })`、`get(id)`、`entitiesIn(x, y, w, h)`、`players`、`events`、`dist(a, b)`、`isAlly(a, b)`、`isVisible(player, x, y)`、`terrain`、`tick`、`rng` |
| 计分和资源 | `addScore`、`setScore`、`addResource` |
| 改实体 | `spawnNear`（找空位刷）、`remove`（移除，不算死亡）、`setHp`、`setOwner`（占领、换主人）、`eliminate`（让玩家出局） |
| 局中改数值 | `setTypeStats(player, type, patch)`、`setStats(id, patch)`（科技、增益） |
| 兵种克制 | 单位定义里写 `attack: { damage, range, cooldown, vs: { cavalry: 3 } }`，打 `cavalry` 伤害乘 3（例子：克制歼灭、克制拓荒） |
| 中立单位 | `orderNeutral(id, { kind: "move" / "attack" / "attackMove" / "stop", … })` |
| 回放里画的 | `setMarkers`（区域、文字）、`setStatus`（顶部状态栏）、`note`（战况和战报里的事件） |
| 限制建筑放哪 | 导出 `buildCheck(ctx, player, type, x, y)`，返回 null 允许、返回字符串就拒绝并告诉 bot |

每个接口的细节（参数、什么时候抛错）见 `RULESET.md` 的「ctx」一节。几条容易踩的：

- **随机数用 `ctx.rng`**，同一个种子永远是同一张图、同一局。
- **`entities()` 拿到的是快照**，改字段没用，每 tick 重新取。
- **每 tick 找某类实体时用筛选**（`entities({ owner, type })`），比取全部实体快得多。

## 7. 限制

规则包和 bot 一样跑在沙箱里：

- **只能 import 自己目录里的文件和 `"rts-arena/standard"`**（平台的标准单位和地图工具），`import type` 随便写。
- **燃料**：加载 2000，`setup` 4000，`onTick` 和 `result` 每次各 400，`objectives` 每次 100，`timeUp` 1000（1 燃料大约 5000 次简单循环）。超了算规则包出错，这一局作废。
- **每局重新加载**：顶层变量每局从头开始，不用自己清零。
- **没有** `Date`、网络、文件、定时器；`console.log` 打到命令行，调试用。

## 8. 发布和分享

- 把整个目录发给别人。对方用 `rts-arena init ./my-rules my-bot` 就能建 bot 目录开始写 bot，用 `rts-arena league ./my-rules a.ts b.ts c.ts` 开联赛。
- 平台升级、或者改了 `objectives.ts` 之后，对目录再运行一次 `rts-arena new-rules ./my-rules`：只刷新平台提供的文件，不动你写的。
- 想做成平台自带的规则包，照着仓库里 `rulesets/<id>/` 的样子放进去。

## 9. 让大模型写规则包

把规则包目录交给编程 agent，提示词可以这样写：

```
请读 RULESET.md，把这个目录改成下面这个玩法：<描述你的玩法>。
每改一版都运行 rts-arena check ./my-rules 和 rts-arena league ./my-rules baseline <其他参考 bot>，看结果再改。
参考 bot 至少写 3 种不同打法，每个文件第一行写一句打法说明；联赛里不要有哪种打法全胜或全败，两边座位的得分率不能偏。
最后告诉我：跑了哪些命令、参考 bot 联赛的结果、结束原因的分布。
```

验收时自己跑一次 `rts-arena check` 和 `rts-arena league`，再用 `rts-arena view` 看几局回放，确认玩起来和你想的一样。
